# تدقيق النسخة القديمة قبل إعادة البناء

تمت مراجعة `main` (v21) والفرع غير المدمج v22. أهم أسباب عدم البناء فوقهما:

## مخاطر علمية

1. مواعيد `HW/LW` تُحسب من طور القمر وخط الطول بمعادلة ثابتة؛ ليست harmonic tide prediction ولا بيانات محطة/نموذج.
2. عبارة «المدّ في تونس ضعيف جداً» تعمم خطأً وتتجاهل خليج قابس، صاحب أكبر نطاقات المدّ في المتوسط.
3. ما سُمي «تياراً جانبياً فيزيائياً» مشتق من `H²/T` واتجاه موج offshore بلا bathymetry أو refraction؛ لا يمكن تقديمه كتيار surf-zone.
4. القيم المفقودة تمر أحياناً عبر `safe_float` فتتحول إلى صفر، وهو خطر لأن غياب الموج/الريح قد يبدو هدوءاً.
5. «نسبة النجاح» ليست مبنية على نتائج مصيد أو calibration، ومع ذلك تعرض كنسبة مئوية وعبارات يقين.
6. نشاط أنواع السمك ومسافة الرمي يقدران بقواعد ثابتة مع معلومات غير كافية عن القاع والعتاد والصياد.
7. تقسيم اليوم إلى أربع كتل كبيرة قد يخفي قفزة خطرة داخل ساعتين.

## مخاطر هندسية

1. ملف backend واحد يقارب 1500–2300 سطر يجمع transport وI/O والفيزياء والصياغة.
2. `GEMINI_API_KEY` مطلوب عند import في main، فيمنع حتى `/health` عند غيابه.
3. قرار حتمي ثم تقرير LLM طويل قد يتعارضان، وزمن الطلب يصل إلى دقائق.
4. المتصفح يجلب raw forecasts ويرسلها للباكند، ما يضاعف المسؤولية وحجم payload ويصعب ضبط المصدر.
5. قائمة الشواطئ الثابتة تتضمن مواقع داخلية/غير ساحلية واتجاهات عامة كثيرة بقيمة 90°.
6. ميزة scan في الفرع المتقدم مفيدة UX، لكنها تعيد استعمال القواعد العلمية نفسها قبل تصحيحها.

## قرار الهجرة

- الاحتفاظ بالنسخة القديمة في تاريخ Git فقط.
- بناء domain جديد typed واختباره من دون شبكة.
- جعل الذكاء الاصطناعي خارج مسار القرار.
- تثبيت عقد v1 ثم إعادة بناء scan والواجهة فوقه، لا نقل الحسابات القديمة كما هي.
